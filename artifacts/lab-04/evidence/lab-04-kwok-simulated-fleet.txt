### 3. Cordon — node-controller response you CAN observe
$ kubectl cordon kwok-node-5
  unschedulable = true
  taint added   = node.kubernetes.io/unschedulable:NoSchedule
  pods already there, untouched = 0

-> Cordon is spec, not status, so it sticks. It stops NEW placement and evicts nothing.

### 4. Why a failed node takes five minutes to fail over
$ kubectl get pod <any> -o jsonpath='{.spec.tolerations}'
  kwok.x-k8s.io/node op=Equal effect=NoSchedule tolerationSeconds=
  node.kubernetes.io/unreachable op=Exists effect=NoExecute tolerationSeconds=10
  node.kubernetes.io/not-ready op=Exists effect=NoExecute tolerationSeconds=10

-> Kubernetes INJECTS these into every Pod. The 300s is not the scheduler being
   slow and it is not a controller backoff — it is a default toleration. Shorten
   tolerationSeconds in the Pod spec and failover happens in seconds instead.

### 5. What KWOK will NOT let you do (measured)
Patching node Ready status:
  $ kubectl patch node kwok-node-1 --subresource=status ... Ready=False
  -> reverted; the node reports Ready=True again within seconds.
  Adding annotation kwok.x-k8s.io/status=custom did not change this, and
  recreating the node with Ready=False in its manifest did not either.

Adding a NoExecute taint:
  $ kubectl taint node kwok-node-11 node.kubernetes.io/unreachable=:NoExecute
  -> applied at t+0, then REMOVED by the kwok-controller. Pods never evict.

-> KWOK owns the node object. It simulates a fleet of HEALTHY nodes very well;
   it is not a node-failure injector. To exercise eviction, use a KWOK Stage
   resource, or take a real kind worker down.
